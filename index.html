Our real results in Python

More processes, how much faster?

Load balancing: the middle of the fractal is harder

How the work is split

  • Why it parallelizes well: every pixel is calculated on its own. No pixel needs another pixel's result.
  • Flynn type: our laptop is MIMD (a multi-core PC, Lecture 2). Our method is data parallelism: the same calculation on different pixels.
  • Memory: the laptop's RAM is shared (UMA), but each Python process has its own memory, so tasks and results travel as messages, like the distributed-memory model in Lecture 2.

Overhead: what it is and how we fix it

The problemEvery task is a message: package it, send it, wait, collect the result. With one pixel per task, that's 38,400 messages for a tiny 240×160 image, and the delivery costs more than the work. Lecture 2 calls this communication overhead.
Fix 1: bigger tasksSend rows instead of pixels. Few messages, lots of work in each. 1 pixel per task took 4.28 s; 256 pixels per task took 0.42 s.
Fix 2: small, but not tiny, chunksThe middle rows are harder than the edges. 4 big strips leave 2 cores idle (2.03 s). Many small chunks keep every core busy (1.53 s). That's load balancing, as in the Lecture 4 load-balancing cluster.
Why never 4× on 4 cores?Starting processes and sending messages cost time, and the laptop lowers its clock when all cores are busy. Her OS slides say it too: "the speed-up ratio with N processors is less than N". Our efficiency: 2.27 ÷ 4 = 57%.

The code (all 3 versions)

Save as mandel.py and run python mandel.py. Our run of this exact file: sequential 3.60 s, parallel 1.48 s (2.43× faster), overhead version 29.23 s.

# Sequential vs parallel Mandelbrot: 3 versions + timings
import time
from multiprocessing import Pool

W, H, MAX_IT = 640, 420, 200

def escape_count(cr, ci):
    zr = zi = 0.0
    n = 0
    while zr * zr + zi * zi <= 4.0 and n < MAX_IT:
        zr, zi = zr * zr - zi * zi + cr, 2 * zr * zi + ci
        n += 1
    return n

def mandel_row(y):
    # one task = one whole row (good parallel)
    ci = -1.2 + 2.4 * y / H
    return [escape_count(-2.2 + 3.0 * x / W, ci) for x in range(W)]

def mandel_pixel(xy):
    # one task = one pixel (overhead version)
    x, y = xy
    return escape_count(-2.2 + 3.0 * x / W, -1.2 + 2.4 * y / H)

if __name__ == "__main__":   # needed on Windows
    t = time.perf_counter()
    seq = [mandel_row(y) for y in range(H)]
    t_seq = time.perf_counter() - t

    t = time.perf_counter()
    with Pool(4) as pool:
        par = pool.map(mandel_row, range(H), chunksize=4)
    t_par = time.perf_counter() - t

    pixels = [(x, y) for y in range(H) for x in range(W)]
    t = time.perf_counter()
    with Pool(4) as pool:
        tiny = pool.map(mandel_pixel, pixels, chunksize=1)
    t_tiny = time.perf_counter() - t

    assert par == seq                                   # same picture
    assert tiny == [n for row in seq for n in row]
    print(f"1. Sequential: {t_seq:.2f} s")
    print(f"2. Parallel:   {t_par:.2f} s  ({t_seq / t_par:.2f}x faster)")
    print(f"3. Overhead:   {t_tiny:.2f} s  (268,800 tiny tasks)")

The 6 points we explain

  1. Why Mandelbrot: heavy, independent work per pixel, so cores can share it with no waiting.
  2. Flynn: MIMD hardware, data-parallel method.
  3. Memory: shared RAM, separate memory per process, data moves as messages.
  4. Speed-up: 2.3× on 4 cores (57% efficiency), not 4×.
  5. Overhead: tiny tasks mean thousands of messages, 9× slower.
  6. Fix: bigger tasks, and small chunks for load balancing.
